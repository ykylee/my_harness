### 증상
- `cargo test --workspace --lib` 실행 시 `add_local::tests::tc_w17_002_non_interactive_with_token` 1 fail
- panic 위치: `crates/llm/src/add_local.rs:620` (현재 line ~664)
- 에러: `called Result::unwrap() on an Err value: BackendUnavailable("set MYHARNESS_LOCAL_LLM_KEY=... env, or install libsecret-1-dev + gnome-keyring for persistent storage")`

### 원인
- test 가 caller 측에서 `KeyringAuthStore::probe()` 1회 (store A) 만들고, `register_local_provider_non_interactive` 내부에서 `KeyringAuthStore::probe()` 다시 호출 (store B)
- `KeyringAuthStore` 의 in-memory cache 가 `Mutex<HashMap<ProviderId, String>>` (instance 별) → store A 와 store B 가 **별개 cache**
- `register_local_provider` 내부 set 은 store B cache 에 들어가서 caller 측 store A cache 에는 없음
- test 가 store A 로 `get` 시도 → cache miss + backend=None → `Err(BackendUnavailable)` → `.unwrap()` panic

### 교훈 (D-62 lesson 확장)
- in-memory cache 가 instance-scoped 이면 caller 와 callee 가 같은 instance 공유 안 함
- 해결: caller 가 store 1개 만들어 함수에 명시 전달 → cache lifecycle 단일화
- back-compat: 기존 fn 시그니처 유지 + 새 `with_store` variant 추가

## 8. 발견된 이슈 갱신

- **AuthStore 의 instance-scoped in-memory cache** (D-62 W19-1): 동일 type 의 여러 instance 가 같은 backend 를 공유하지 않음 (의도된 설계이나 caller-주도 cache lifecycle 필요). v1.5+ 에서 `KeyringAuthStore` 가 `Arc<KeyringAuthStore>` (process-wide shared) 또는 static LazyLock 가 되면 caller-주도 lifecycle 불요. 현 v1.5+ 에서는 caller 가 store 1개 만들어 명시 전달 패턴 권장
- **libsecret 부재 환경 BackendUnavailable** (KeyringAuthStore::get): in-memory cache hit → Ok, miss → Err (의도된 v1 동작). 영구 저장 미지원 환경에서는 set → get 사이클만 동작, clear 후 재시도 시 Err. v1.5+ 에서 in-memory cache 만으로 동작하도록 backend=None 도 Ok(None) 으로 softening 검토 (단, 사용자 혼동 방지 위해 warn log 추가)

## 10. D-64 (2026-06-10) — W21 F-1+F-2 통합 (backup filename `<ts>.<sha256_8>` + sort bug fix)

### 결정 배경
- F-1 (monotonic_ts) + F-2 (git-style versioning) 단독 검토 시 각각 효과 제한
- F-1: sub-second 충돌 방지하나 corruption 미검증
- F-2: content hash 로 collision + corruption 동시 해결, sha2=0.10 이미 auth crate 에 있음
- **F-1+F-2 통합** = `<unix_ts>.<sha256_8>` 한 사이클로 R-5-A/B + sort bug 동시 해결

### 3가지 Risk (구현 결정 근거)

#### R-5-A: Sub-second collision
- 기존 `as_secs()` 만 사용 시 동일 second 내 rapid register → 동일 filename → 앞 backup 덮어쓰기
- TC-W18-001/002 가 `sleep(1100ms)` 로 workaround 했음 (이제 불요)
- **해결**: hash8 으로 동일 ts 내 다른 content → 다른 hash → 다른 filename

#### R-5-B: Content 식별 불가
- 기존 filename = `<ts>` only → user 가 어떤 backup 이 어떤 content 인지 모름
- **해결**: hash8 = SHA-256(content)[:8] → backup file 의 content snapshot fingerprint

#### Sort bug (W21 background 분석에서 추가 발견)
- `cleanup_old_backups` 가 `sort_by_key(|e| e.file_name())` (string sort) 사용
- `backup.999` (string 정렬 시 4번째) vs `backup.10000` (string 정렬 시 1번째)
- '9' > '1' 으로 retention **거꾸로 동작** — 더 오래된 것이 살아남고, 더 새로운 것이 삭제됨
- **해결**: `parse unix_ts` numeric sort

### 구현

#### hash8 util (신규)
- `myharness/crates/llm/src/hash8.rs`
- `content_hash_8(content: &[u8]) -> String` — SHA-256 → hex 8-char truncate

- 3 L1 test (identical/different/empty)

#### backup 함수 3개 리팩토링

- `with_backup_suffix`: signature `(path, ts: u64, hash8: &str) -> PathBuf`, format = `<base>.backup.<ts>.<hash8>`
- `cleanup_old_backups`: **sort fix** — `parse unix_ts` numeric sort (string sort 거꾸로 retention 수정)
